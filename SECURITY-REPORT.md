# Отчёт по аудиту безопасности `script.py`

**Дата:** 2026-10-08
**Объект:** `script.py` — загрузка файлов из Seafile через Web API с последующим удалением на сервере (запуск из cron каждые 5 минут)
**Базовая версия:** коммит `44d2096` (`feat(seafile): download and delete script`)
**Окружение проверки:** macOS (Darwin 24.6.0), Python 3.14.4, curl 8.7.1
**Итог:** критичных и высокоопасных уязвимостей не найдено. Устранено 8 замечаний (1 среднего уровня, 1 низкого/среднего, 6 низкого уровня и hardening). 6 замечаний по валидации конфигурации и документации вынесены в `plan.md` и не исправлялись.

## 2. Устранённые проблемы

### 2.1. Скачанный файл мог стать доступным на запись всем — **средний уровень**

**Было** (`script.py:341-347`):
```python
umask = os.umask(0)
os.umask(umask)
os.chmod(tmp_path, 0o666 & ~umask)
```

**Суть.** `mkstemp` создаёт файл с правами `600`, и скрипт осознанно расширял их по umask процесса, чтобы данные могли читать другие сервисы. Но база `0o666` даёт право на **запись**, а не только на чтение:

| umask процесса | Итоговые права |
|---|---|
| `022` (типичная) | `644` — безопасно |
| `002` | `664` — запись для группы |
| `000` (встречается в systemd-юнитах и части cron-окружений) | `666` — **запись для всех** |

Любой локальный пользователь смог бы подменить содержимое файла, который читают другие сервисы, уже после всех проверок целостности.

**Стало** (`script.py:341-347`):
```python
umask = os.umask(0)
os.umask(umask)
os.chmod(tmp_path, 0o644 & ~umask)
```

Право на запись остаётся только владельцу при любом umask; чтение по-прежнему открывается по umask.

### 2.2. Пути из argv и окружения не проверялись на управляющие символы — **низкий уровень**

**Было** (`script.py:124-135`). `sys.argv`, `SEAFILE_PATHS` и `SEAFILE_PATH` читаются напрямую через `os.environ.get`/`sys.argv`, минуя функцию `env()`, которая прогоняет значения через `check_value`. В URL это безопасно — всё кодируется `quote` — но строка в исходном виде попадала:

* в `log()` — инъекция в лог и ESC-последовательности в терминале оператора;
* в имя локального файла через `os.path.basename`.

**Стало** (`script.py:136-141`):
```python
# argv и SEAFILE_PATHS читаются минуя env(), поэтому проверяем здесь:
# управляющие символы иначе попадут в лог и в имя локального файла.
try:
    check_value(p, f"путь {p!r}")
except ValueError as e:
    fail_config(str(e))
```

Проверка выполняется до нормализации пути, то есть покрывает все три источника списка файлов.

### 2.3. Lock-файл в общем `/tmp` — **низкий/средний уровень**

**Было** (`script.py:346-354`):
```python
lock_path = os.path.join(tempfile.gettempdir(), f"seafile_fetch_{REPO}.lock")
lock_fd = os.open(lock_path, os.O_CREAT | os.O_RDWR | os.O_NOFOLLOW, 0o600)
try:
    fcntl.flock(lock_fd, fcntl.LOCK_EX | fcntl.LOCK_NB)
except BlockingIOError:
    log("Предыдущий запуск ещё работает, выходим")
    return 0
```

**Суть.** `O_NOFOLLOW` закрывал подмену симлинком, но не squatting: имя файла предсказуемо (`REPO` известен), а `/tmp` доступна на запись всем. Посторонний локальный пользователь мог заранее создать файл с этим именем и:

1. держать на нём `flock` сколько угодно — скрипт при каждом запуске писал «Предыдущий запуск ещё работает» и возвращал **0**, то есть cron считал запуск успешным, а данные тихо не забирались неограниченно долго;
2. либо выставить права `0600` под собой — `os.open` падал с `EACCES`, исключение всплывало до обработчика в `__main__` и логировалось общим сообщением без указания причины.

Исправления сделаны в четырёх частях.

**(а) Приватный каталог вместо `/tmp`** (`script.py:363-370`):
```python
def lock_dir():
    """Приватный каталог для lock-файла. В общей /tmp посторонний может заранее
    создать файл с таким именем и держать его заблокированным (или закрыть к нему
    доступ), и запуски будут молча пропускаться."""
    for d in (os.environ.get("XDG_RUNTIME_DIR"), f"/run/user/{os.getuid()}", DEST_DIR):
        if d and os.path.isdir(d) and os.access(d, os.W_OK):
            return d
    return DEST_DIR
```
Имя файла стало скрытым (`.seafile_fetch_<REPO>.lock`), чтобы не мешать, если резервным вариантом оказался `DEST_DIR` (`script.py:378`).

**(б) Проверка владельца** (`script.py:384-386`):
```python
if os.fstat(lock_fd).st_uid != os.getuid():
    log(f"ОШИБКА: lock-файл {lock_path} принадлежит другому пользователю")
    return 2
```
Проверка через `fstat` на уже открытом дескрипторе, а не `stat` по пути — без TOCTOU-окна между проверкой и использованием.

**(в) Явная обработка `OSError`** (`script.py:379-383`):
```python
try:
    lock_fd = os.open(lock_path, os.O_CREAT | os.O_RDWR | os.O_NOFOLLOW, 0o600)
except OSError as e:
    log(f"ОШИБКА: не удалось открыть lock-файл {lock_path}: {e}")
    return 2
```

**(г) Отдельный код выхода при занятом lock** (`script.py:390-392`):
```python
except BlockingIOError:
    # Код 3, а не 0: иначе навсегда занятый lock выглядит для cron как успех.
    log("Предыдущий запуск ещё работает, выходим")
    return 3
```

> **Изменение поведения.** Раньше занятый lock был успехом (код 0). Теперь это код 3, и cron/мониторинг начнёт на него реагировать. Строка про коды выхода в docstring обновлена (`script.py:32-33`). Если такое поведение нежелательно, возврат 0 восстанавливается правкой одной строки — но тогда вернётся исходная проблема: бесконечно удерживаемый lock останется невидимым для мониторинга.

### 2.4. Не было ограничения на размер загрузки — **низкий уровень**

**Было** (`script.py:311` в исходной версии): `curl(dl_url, output=tmp_path, auth=False)` — скачивание без лимита при `--max-time 300`. Размер файла уже известен из `file/detail/`, но сверка выполнялась только **после** полной загрузки, так что аномально большой ответ успевал заполнить диск.

**Стало.** Параметр в `curl()` (`script.py:184`, `189`, `209-210`):
```python
if max_filesize is not None:
    cmd += ["--max-filesize", str(max_filesize)]
```
и его использование при скачивании (`script.py:327-330`):
```python
# Предел размера: оборвать загрузку, если сервер отдаёт больше обещанного,
# не дожидаясь заполнения диска (для пустого файла предел не ставим).
code, _ = curl(dl_url, output=tmp_path, auth=False,
               max_filesize=remote_size if remote_size > 0 else None)
```

Лимит ставится ровно по объявленному серверу размеру. Для пустого файла (`remote_size == 0`) лимит не передаётся, поскольку трактовка значения `0` у `--max-filesize` неоднозначна между версиями curl.

> **Остаточное ограничение.** `--max-filesize` срабатывает по заголовку `Content-Length`; ответ без него (chunked transfer encoding) лимит обойдёт. Поэтому основной проверкой остаётся сверка `os.path.getsize(tmp_path) != remote_size` после загрузки (`script.py:337-340`), а лимит — защита от заполнения диска в типичном случае.

### 2.5. `curl` искался по `PATH` при каждом вызове — **низкий уровень**

**Было** (`script.py:186` в исходной версии): `cmd = ["curl", "-q", ...]`. `CURL_ENV` наследует `PATH` от родительского процесса, и `subprocess` искал исполняемый файл по нему при каждом запросе. В cron-окружении с неаккуратным `PATH` (относительный элемент вроде `.` или каталог, доступный на запись посторонним) это даёт подмену исполняемого файла, то есть выполнение чужого кода с правами скрипта и доступом к токену.

**Стало** (`script.py:115-119`):
```python
# curl ищется один раз и только по абсолютному пути: относительный элемент в PATH
# (или каталог, доступный на запись) иначе позволил бы подставить свой curl.
CURL = shutil.which("curl", path=CURL_ENV.get("PATH", os.defpath))
if not CURL or not os.path.isabs(CURL):
    fail_config("curl не найден в PATH либо найден не по абсолютному пути")
```
и использование в команде (`script.py:200`): `CURL, "-q",`.

Три эффекта: поиск происходит один раз при старте (а не на каждый из 4 запросов на файл), относительный путь отвергается явной ошибкой конфигурации, и отсутствие curl диагностируется при запуске, а не падением первого запроса.

## 3. Проверка исправлений

Поднят локальный https-сервер, имитирующий нужные эндпоинты Seafile API (`/api2/ping/`, `/api2/auth/ping/`, `file/detail/`, `file/`, скачивание, `DELETE`), с самоподписанным сертификатом на `localhost` и доверием через `CURL_CA_BUNDLE`. Скрипт запускался с полностью урезанным окружением (`env -i`), чтобы исключить влияние локальных настроек.

| № | Сценарий | Ожидание | Результат |
|---|---|---|---|
| A | Нормальная загрузка при `umask 000` | `exit 0`, права `644` | ✅ `exit 0`, `-rw-r--r--`, 100 байт, удаление в Seafile прошло (до правки было бы `-rw-rw-rw-`) |
| B | Сервер объявляет 100 байт, отдаёт 50 МБ | обрыв загрузки, файл не заменён | ✅ `curl (63) Maximum file size exceeded`, `exit 1`, локальный файл не создан, в Seafile не удалён |
| C | Lock удерживается другим процессом | `exit 3` | ✅ «Предыдущий запуск ещё работает», `exit 3` |
| D | Lock-файл недоступен (права `000`) | явная ошибка, `exit 2` | ✅ `Errno 13 Permission denied` с путём, `exit 2` (раньше — общая ошибка и `exit 1`) |
| E | На месте lock-файла симлинк на `/etc/hosts` | отказ, `exit 2` | ✅ `Errno 62 Too many levels of symbolic links`, `exit 2` — `O_NOFOLLOW` работает |
| F | Не задан `SEAFILE_URL` | `exit 2` | ✅ «переменная SEAFILE_URL не задана» |
| G | Путь с `\n` в argv | `exit 2` | ✅ «путь `'/a\nheader = x'`: недопустимый управляющий символ» |

Дополнительно: `python3 -m py_compile script.py` проходит; `curl 8.7.1` поддерживает `--max-filesize` (проверено по `curl --help all`).

**Не покрыто тестом:** проверка `st_uid` (п. 2.3б) — для неё нужен lock-файл, принадлежащий другому пользователю, то есть root. Логика состоит из трёх строк, а путь отказа при открытии чужого файла покрыт сценарием D.

## 4. Что не исправлялось

Эти пункты остались в `plan.md` неотмеченными — они не про безопасность (валидация конфигурации и документация):

* `parse_base_url` пропускает `SEAFILE_URL` с пустым фрагментом (`https://host/#`): проверка `u.fragment` не срабатывает, потому что фрагмент — пустая строка, и все дальнейшие пути уедут во фрагмент. Это ломает работу при такой опечатке, но не ослабляет защиту.
* `is_trusted_url` сравнивает `netloc` как строку, поэтому `https://host:443/...` не равно `https://host/...`. Поведение fail-closed (запрос отклоняется), то есть безопасное, но ломает конфигурации, где Seafile отдаёт download-ссылку с явным портом.
* Нет поддержки отдельного хоста файл-сервера (`FILE_SERVER_ROOT`) — по той же причине.
* Расширение блока «Меры безопасности» в docstring.
* Документирование архитектурного риска: файл удаляется из Seafile сразу после локальной замены, поэтому до вычитки единственная копия данных лежит на локальном диске. Нужен бэкап `DEST_DIR` либо отложенное удаление. Это не дефект кода, а свойство задуманной схемы, но оно определяет требования к эксплуатации.
* Ручной прогон остальных сценариев (битый JSON в `file/detail/`, несовпадение размера, недоверенная download-ссылка).

Отдельно, как информация к сведению: целостность проверяется только по размеру. По TLS этого достаточно, так что это не уязвимость, но подмена на стороне сервера файлом того же размера проверку пройдёт. Seafile возвращает в `file/detail/` поле `id` (собственный хеш), сверка по нему была бы строже.
